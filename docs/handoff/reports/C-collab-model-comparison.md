# C5. 협업 모델 비교 초안

**한 줄 결론:** 현재 전체 문서 저장은 구현·운영 부담이 가장 작지만 충돌 단위가 넓다. 요소별 patch 또는 CRDT 전환은 실제 동시 편집 요구를 먼저 정해야 한다.

## 한 것 / 못 한 것

- 현재 `WorkflowEditorDocumentService`의 행 잠금, `expectedVersion` 409, 버전 증가, commit 후 graph 알림과 재접속 snapshot/변경 로그를 기준으로 비교했다. 새 모델 구현과 성능 시험은 하지 않았다.

| 기준 | 현재 DB 전체 문서 | 요소별 조건부 patch | Yjs CRDT |
|---|---|---|---|
| 충돌 | 문서 버전 단위 409; 독립 요소도 충돌 | 요소 버전 단위 409 | 공유 문서 병합; 의미 충돌은 별도 규칙 |
| 재접속 | snapshot + graphSeq replay, 오래된 로그는 reset | 요소별 로그/스냅샷 필요 | 상태 벡터/업데이트 영속화 필요 |
| undo | 로컬 명령 기록과 서버 버전 충돌 조정 | 요소별 역명령·의존성 필요 | Yjs UndoManager 등 범위 설계 필요 |
| 권한 철회 | 요청마다 DB 권한 확인 | patch마다 확인 | 업데이트 수신·송신 양쪽 ACL과 세션 차단 필요 |
| 운영 복잡도 | 현재 DB·Redis 유지 | patch 순서·로그·정리 추가 | provider·문서 저장·압축·관측 추가 |
| 구현 비용 | 현재 수준 유지 | 중간 | 높음, 시제품과 데이터 전환 필요 |

현재 첫 문서 동시 생성에는 잠글 행이 없어 별도 원자성 설계가 필요하다. 모델 선택과 관계없이 권한 철회 시 열린 STOMP 세션 처리, DB commit 뒤 Redis 장애에 따른 누락, 실제 두 브라우저 실험이 남는다.

## 사람 결정이 필요한 것

- D1: 주 사용 패턴(동시 작성자 수, 같은 요소 동시 편집 빈도, offline 필요)과 허용 가능한 충돌 UX를 정한다.

## 다른 담당에게 넘길 것

- **제품·협업 설계 담당:** 측정 시나리오를 정하고 현재 모델의 409 빈도부터 수집한다.
