# ADR-006: 노드 종류(Operation Type)와 분기·합류 규칙

작성일: 2026-10-11

## 상태

**Accepted (2026-10-17, 사용자 결정 "Accept as recommended"). 구현 전.** 2026-10-11에 Proposed 초안으로 썼고(사용자 요청 "Proposed ADR 초안만 작성"), 사용자가 아래 결정으로 수용 기준을 닫았다. 승인과 구현은 별개다: 구현은 리드의 설비 효율(2ea) 다음에 Exclusive부터 한다. Join·Subflow·수량 분할은 이 ADR에서 승인하지 않은 후속 단계다.

근거: [벤치마크](../../reference/benchmarks/FlowMat_GitHub_Benchmark_2026-09-24.md) FM-PLAN-001(frePPLe operation의 fixed_time·time_per·routing·alternate·split, FlowMat 표현 ATOMIC·ROUTING·ALTERNATE·SPLIT·JOIN·SUBFLOW, 시간 정책 FIXED_TIME·TIME_PER_UNIT·FORMULA), [ADR-004](ADR-004-flow-run-execution-policy.md)가 참고한 Conductor의 흐름 제어 개념(분기·병렬·합류·하위 흐름). 코드는 가져오지 않는다.

## 배경 (2026-10-11 코드 기준)

- 노드 종류 `process.node_type`(process·equipment·storage·input·output)은 화면 분류일 뿐 실행 의미가 없다.
- 그래프 실행([포트·연결 계약](../../domain/process-port-connection-contract.md) GR-04): 출발 단계가 끝나면 조건을 통과한 **모든** 연결마다 대상 단계를 **따로** 만든다. 그래서 지금은
  - 순차(ROUTING): 연결 하나로 이미 된다.
  - 포함 분기: 조건이 여러 개 참이면 여러 갈래로 간다(지금 동작).
  - 배타 선택(하나만 고르기): 없다. 조건을 서로 겹치지 않게 적어야만 흉내 낸다.
  - 병렬 분기(SPLIT/fork): 조건 없는 연결 여러 개로 흉내 낸다. 수량은 나누지 않고 각 갈래가 같은 출력 스냅샷을 받는다.
  - 합류(JOIN): 없다. 진입 연결마다 별도 단계라 "모두 도착하면 한 번"이 되지 않는다([실행 모델](../execution-model.md) §5 "여러 연결의 합류와 수량 분할").
  - 하위 흐름(SUBFLOW): 없다.
- 순환 그래프는 실행을 거절한다(GR-01). 루프는 범위 밖이다.
- 시간: 실행 엔진의 시간은 노드 정책의 시간 제한·재시도 간격(ADR-004)뿐이다. 계획 쪽은 설비의 시간당 산출·전환 시간으로 작업지시 일정을 따로 계산한다.
- 서버는 단계를 스스로 시작·완료하지 않는다(ADR-004 결정 3, 외부 보고 방식).

## 선택지

| 안 | 내용 | 좋은 점 | 약점 |
|---|---|---|---|
| A | 노드에 `operation_type` 열(ATOMIC 기본·EXCLUSIVE·PARALLEL·JOIN·SUBFLOW)을 두고, 그 노드의 나가는·들어오는 연결 해석을 바꾼다 | 노드 수가 그대로다. 기존 그래프는 ATOMIC = 지금 동작 | 한 노드가 "할 일"과 "흐름 규칙"을 함께 진다. 분기와 합류를 한 노드에 두면 해석이 복잡하다 |
| B | 일을 하지 않는 **게이트웨이 노드 종류**(Exclusive·Join, 필요하면 Parallel)를 더한다. 게이트웨이 단계는 보고 없이 서버가 바로 통과시킨다 | 흐름 규칙이 화면에 보인다. 엔진 규칙이 노드 종류마다 나뉜다 | 노드가 늘어난다. "서버는 단계를 대신 완료하지 않는다"(ADR-004 결정 3)의 첫 예외가 생긴다 |
| C | 연결에 `branch_mode`·`priority`를, 대상 노드에 `join_mode`(any·all)를 둔다 | 바뀌는 곳이 가장 적다 | 규칙이 연결과 노드에 흩어져 그림으로 읽기 어렵다 |

## 결정 (2026-10-17)

1. **B(게이트웨이 노드)로, 1단계는 Exclusive만.** 병렬 분기는 지금 동작(조건 없는 여러 연결)과 같으므로 노드를 새로 만들지 않는다.
2. **Exclusive:** 나가는 연결에 순서(`priority`, 작은 수 먼저)를 두고, 조건을 만족하는 **첫** 연결 하나만 단계를 만든다.
3. **기본 연결은 Exclusive마다 최대 하나.** 조건을 만족하는 연결이 없으면 기본 연결로 가고, 기본 연결도 없으면 실행 실패(연결 실패 정책과 같은 기록).
4. **게이트웨이 단계만 서버가 바로 완료한다**(actor `system`, 이벤트 기록). ADR-004 결정 3의 좁은 예외로 이 ADR에 적는다. 일반 노드는 지금처럼 외부 보고만 받는다.
5. 게이트웨이는 재고·생산 기록을 움직이지 않는다. 생산 실행([실행 모델](../execution-model.md) §6)의 부수효과 규칙은 그대로다.
6. 발행 snapshot에 게이트웨이 종류·연결 순서·기본 연결이 들어가고 실행 중에는 바뀌지 않는다(ADR-003 결정 5, ADR-004 결정 1과 같은 원칙). 이전 revision은 지금처럼 돈다.
7. **시간 정책**(FIXED_TIME·TIME_PER_UNIT·FORMULA)은 실행 엔진이 아니라 계획 영역(FM-PLAN-002 용량 자원·FM-PLAN-003 달력, 작업지시 일정)에 둔다. 노드에 소요 시간 열을 두지 않는다.
8. 화면: 팔레트에 Exclusive, 연결 인스펙터에 순서와 "기본 연결", 워크플로 검사에 새 경고(Exclusive에 나가는 연결이 하나뿐, 기본 연결이 둘 이상 등).
9. **Join은 승인하지 않는다.** "이번 실행에서 실제로 출발한 갈래를 기다린다"만으로는 먼저 도착한 갈래가 합류를 일찍 끝내는 문제를 막기 어렵다. 중첩 분기, 건너뛰거나 실패한 갈래, 재시도로 같은 갈래가 두 번 도착하는 경우의 기준을 정한 뒤 별도 결정으로 다룬다.

## 수용 기준 (2026-10-17 사용자 확정)

- [x] 표현 방식: **B(게이트웨이 노드)**
- [x] 1단계 범위: **Exclusive만**(Join·Parallel·Subflow는 후속)
- [x] Exclusive에서 만족하는 연결이 없을 때: **기본 연결(최대 하나), 없으면 실패**
- [x] Join 기준: **이 ADR에서 정하지 않는다**(아래 "결정하지 않은 것")
- [x] 게이트웨이 단계를 서버가 바로 완료하는 예외(ADR-004 결정 3): **게이트웨이에만 허용, system 이벤트 기록**
- [x] 시간 정책은 계획 쪽에 둔다(실행 엔진에 소요 시간 없음)

## 결정하지 않은 것

- Join(합류) 전체: 기다릴 갈래의 기준, 중첩 분기, 건너뛰거나 실패한 갈래, 재시도 중복 도착, 합친 입력 스냅샷의 모양
- 수량 분할(SPLIT의 수량 나눔)과 합류 때 수량 합산 규칙
- 하위 흐름(SUBFLOW)의 revision 고정·권한
- 대체 자원·대체 경로(frePPLe alternate)
- 루프(지금은 순환 그래프 거절)
- 노드 자동 실행기(ADR-004 결정하지 않은 것과 같음)

## 결과

- 좋은 점
  - 배타 선택과 합류를 조건 꼼수 없이 그릴 수 있다. 기존 그래프와 실행은 그대로다.
  - 계획(시간)과 실행(흐름)이 섞이지 않는다.
- 위험
  - 서버가 스스로 완료하는 단계가 처음 생긴다. 이벤트·감사 기록과 동시성(같은 실행 행 잠금) 규칙을 함께 정해야 한다.
  - (후속) Join의 "출발한 갈래" 계산이 skip·재시도·Exclusive와 얽힌다. 그래서 1단계에서 빼고 별도로 결정한다.
